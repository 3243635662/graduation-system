## 二、必须修复的问题

### 2.1 重新设计“当前关系唯一 + 历史关系保留”

v1.1 §5.3 的以下方案不能使用：

```prisma
@@unique([batchStudentId, endedAt])
```

同样问题也存在于：

- `StudentTopicAssignment` 的 `(topicId, endedAt)`；
- `StudentTopicAssignment` 的 `(batchStudentId, endedAt)`；
- `ReviewerAssignment` 等类似关系。

原因：MySQL 8.4 的 UNIQUE 索引允许同一唯一键中出现多条包含 NULL 的记录。因此，多个 `endedAt = NULL` 的当前关系可以同时存在；另外，Prisma 对复合唯一字段还有非空约束要求。不能将该方案描述为“数据库保证只有一条有效关系”。

请重新设计并给出可在 MySQL 8.4 + Prisma 7 中可靠实施的方案。优先评估**当前关系表 + 历史关系表**：

- 当前关系表通过 `batchStudentId @unique` 保证同一学生同批次只有一条当前课题/主指导/评阅关系；课题当前关系表同时通过 `topicId @unique` 保证一题一生。
- 历史关系表保留每次建立、终止、更换的关系快照，包括原关系 ID、批次学生、课题/教师、开始结束时间、变更原因、操作人、来源。
- 当前关系变更与历史记录写入必须在同一事务内完成。
- 说明如何避免“更新当前关系成功但历史写入失败”或相反的部分状态。
- 明确查询当前关系和历史关系的 API/领域服务职责。

也可以提出经 MySQL 实测且 Prisma Schema / migration diff 可长期维护的其他方案，但必须提供最小 SQL 验证，证明重复插入两条当前关系会被数据库拒绝，同时允许多条历史记录存在。不能只靠应用层查询后再插入来声称数据库唯一。

### 2.2 双向选择状态机不得绕过学生确认

v1.1 §6.2 中“管理员强制确认（跳过学生确认）”与已经确认的双向选择流程不一致。请删除这条状态迁移。

正确区分：

- **双向选择**：学生填报志愿 → 课题教师表达意向 → 学生接受或拒绝 → 双方达成一致 → 学院处理冲突/未匹配 → 管理员最终确认。
- **学校手动分配**：管理员直接分配，确认后立即生效，不需要学生二次确认。

管理员如需在双向选择失败后直接安排学生，应结束/关闭原双向选择流程，再通过独立的 MANUAL 分配命令执行；必须记录原因和来源，不能伪装成学生已经接受。

同时确认：一个课题只能由一名学生占用；一个学生同批次只能有一个当前课题和一名主指导教师；历史不能覆盖。

### 2.3 明确 Excel 分配导入的字段与关系

手动分配已确定支持单个、批量及 Excel 导入，并且课题分配和指导教师分配是两条独立关系。

请把导入场景定义清楚，至少区分：

- 仅分配课题；
- 仅分配指导教师；
- 同时分配课题和指导教师。

导入必须先预览、逐行校验、确认后调用领域分配服务；不能直接批量写 Prisma。说明原子导入与部分成功模式的默认策略，并确保一题一生、教师指导人数、批次归属、学生资格等规则统一校验。

### 2.4 学院配置范围要与已确认需求一致

v1.1 §16 建议学院只可覆盖“阶段时间、材料截止、是否需要学院审核”三项，范围过窄。

请按已确认需求整理允许配置项，至少覆盖：

- 阶段起止时间；
- 是否启用学校定义的可选阶段；
- 学校定义的材料类型在当前批次/学院是否必交或选交，以及允许的文件格式、大小、截止时间；
- 是否需要学院审核及对应审核责任配置；
- 逾期补交规则。

仍采用“学校统一主流程 + 学院有限配置”，不允许学院任意改变核心流程顺序，不建设通用工作流引擎。不要把未经确认的专业级全量配置覆盖能力擅自加入范围。

### 2.5 班级加入申请必须保留三种入口

已确认的组织加入方式包括：

- 学号信息；
- 邀请码；
- 组织搜索。

v1.1 将邀请码降为 P2，和已确认需求不一致。请将三种入口全部纳入目标需求；具体开发阶段可以说明最小实现先后，但不能从规格中删除或擅自降为“不做”。

班级加入申请只改变当前组织归属并写 `StudentClassTransfer`，不能自动创建 `BatchStudent`，也不能自动授予任何角色。

### 2.6 文件下载接口避免把短期令牌放在 URL 查询参数

v1.1 使用 `GET /files/stream?token=...`。请重新评估令牌通过 URL 传递可能进入代理日志、浏览器历史或监控日志的问题。

优先考虑：

- 认证后的业务子资源下载接口，例如 `GET /material-versions/:id/download`；
- 服务端实时校验当前 Token、角色、批次参与关系、指导/评阅关系，再流式返回私有文件；
- 若确有短时下载凭证需求，凭证不要放在 URL 中，需绑定用户/会话、短时有效、一次性使用，并防止重放。

始终禁止公开文件 URL 和 `GET /files/:id` 这种仅凭 fileId 下载的接口。协管员仍只能看到材料状态，不得下载正文。

## 三、需要核对并修订的已确认需求

1. 单一 Vue Web 应用；不开发 Flutter App 和微信小程序。
2. 五类角色工作台保留在同一个 Vue 应用内；角色并存与切换不改变后端权限。
3. 成绩默认权重 30% / 30% / 40%，支持配置；权重总和必须校验为 100%。
4. 学生原则上一个当前有效毕业批次；延期时保留旧批次记录并进入新批次。不要将“原则上”误写成无例外的数据库唯一约束；建议默认规则在服务层执行，特殊例外是否开放需明确记录。
5. 站内通知第一阶段只做站内通知，不提前引入短信、邮件、微信通知渠道。

7. 公共知识库和个人材料知识库分层；Chroma 已在 compose 中预置，但应用侧集成属于后续阶段。
8. 协管资格按学生本班在籍、非学生工作人员所属院系一致、学校特殊覆盖三类；不要求班长/班助任职。
9. 协管退出申请保留；协管申诉和自主申请成为协管员不开发。
10. 线下答辩为第一阶段方式；答辩小组统一最终评分，支持手工录入和 Excel 导入；不要求评委逐人登录打分。
